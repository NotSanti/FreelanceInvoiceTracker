# FreelanceInvoiceTracker Security Cleanup Plan

**Repository:** `NotSanti/FreelanceInvoiceTracker`  
**Audited branch / commit:** `main` at `95b21a3`  
**Audit date:** 2026-09-08  
**Primary stack:** Next.js 16, React 19, Supabase Auth/Postgres, Stripe Checkout, Resend, Web Push

## Purpose

This is an implementation plan for a coding agent. Apply it incrementally. Do not combine the database boundary fix, Stripe changes, public-page privacy changes, and dependency upgrades into one large commit.

The review covered the current source tree and all six Git commits, including:

- committed secrets and sensitive configuration;
- Supabase tables, grants, RLS policies, foreign keys, and `security definer` functions;
- authentication and route protection;
- public invoice links and exposed invoice/client fields;
- all API routes and server actions;
- Stripe Checkout and webhook processing;
- Web Push subscriptions;
- HTML/email rendering and PDF downloads;
- input validation, security headers, dependencies, tests, and CI posture.

This is a static repository review, not proof of the deployed configuration. The live Supabase, Stripe, Vercel, Resend, DNS, and GitHub settings must be verified using the dashboard checklist near the end.

## Executive summary

The project has a sound starting posture: RLS is enabled on the application tables, `anon` table access is revoked, authenticated queries use Supabase `getUser()`, Stripe webhook signatures are checked against the raw body, service-role access is server-side, email HTML is escaped, PDF filenames are sanitized, and no live-looking credentials were found in the current tree or Git history.

Do not treat the application as production-ready yet. The most important confirmed issue is an incomplete tenant relationship between `invoices` and `clients`. Application code checks client ownership, but the database does not enforce it. A direct authenticated Supabase request can create or update an invoice whose `user_id` belongs to the attacker while its `client_id` references another account. The public invoice `security definer` RPC then joins and returns that client's identifying data. Knowing another client's UUID is required, but tenant isolation must not depend on UUID secrecy.

The next priorities are payment concurrency/integrity, a critical advisory in the locked Vitest version, public bearer-link privacy, abuse controls, and hardening privileged database functions.

## Phase 2 — Close the cross-tenant client/invoice boundary (highest priority)

### Why

`public.invoices` has independent foreign keys for `user_id` and `client_id`. Its RLS `WITH CHECK` only verifies `auth.uid() = user_id`. The application calls `assertOwnedClient`, but a logged-in user can call the Supabase REST API directly and bypass that application check. Database authorization must validate the relationship itself.

### Migration preflight

Run this before adding constraints. It must return zero rows:

```sql
select
  i.id as invoice_id,
  i.user_id as invoice_user_id,
  i.client_id,
  c.user_id as client_user_id
from public.invoices i
join public.clients c on c.id = i.client_id
where i.user_id <> c.user_id;
```

If rows exist, stop. Export the affected identifiers, determine the correct owner manually, and repair them before validating a constraint. Do not delete financial records automatically.

### Migration tasks

Create a new migration that:

1. Adds a unique constraint usable by a composite foreign key:

```sql
alter table public.clients
  add constraint clients_id_user_id_unique unique (id, user_id);
```

2. Replaces the single-column invoice/client foreign key with a tenant-bound composite foreign key:

```sql
alter table public.invoices
  drop constraint if exists invoices_client_id_fkey;

alter table public.invoices
  add constraint invoices_client_owner_fkey
  foreign key (client_id, user_id)
  references public.clients (id, user_id)
  on delete restrict;
```

Use the actual deployed constraint name after inspecting `pg_constraint`; do not assume drift-free naming.

3. Recreates invoice insert and update policies so `WITH CHECK` verifies both the invoice owner and the selected client owner. Keep the composite FK even with the policy; they provide independent defense in depth.

```sql
with check (
  (select auth.uid()) = user_id
  and exists (
    select 1
    from public.clients c
    where c.id = client_id
      and c.user_id = (select auth.uid())
  )
)
```

Qualify ambiguous columns with table aliases in the final migration.

4. Add equivalent relational integrity for payments so even service-role code cannot mismatch `payments.user_id` and the referenced invoice owner:

```sql
alter table public.invoices
  add constraint invoices_id_user_id_unique unique (id, user_id);

alter table public.payments
  drop constraint if exists payments_invoice_id_fkey;

alter table public.payments
  add constraint payments_invoice_owner_fkey
  foreign key (invoice_id, user_id)
  references public.invoices (id, user_id)
  on delete cascade;
```

### Database tests

Add pgTAP tests under `supabase/tests/`. Use two users, A and B, with separate profiles and clients.

Test all of these explicitly:

- A can create/read/update/delete A's client.
- A cannot read/update/delete B's client.
- A can create an invoice using A's client.
- A cannot create an invoice with `user_id = A` and `client_id = B's client`.
- A cannot update A's invoice to point to B's client.
- A cannot insert/read/update/delete invoice items on B's invoice.
- A cannot insert a payment for B's invoice.
- A cannot set `payments.user_id = A` for an invoice owned by B.
- `anon` cannot directly select/insert/update/delete any business table.
- The public RPC with A's valid sent-invoice token returns only A's expected invoice/client payload.
- A random token and a draft/void invoice token return no public payload.

Run:

```bash

npm test

```

## Phase 3 — Harden public and privileged database functions

### Files

- `supabase/migrations/20260901212000_public_invoice_and_indexes.sql` (reference only; do not edit)
- `supabase/migrations/20260901212500_invoice_checkout_state.sql` (reference only)
- `supabase/migrations/20260901213000_restrict_checkout_rpc.sql` (reference only)
- `supabase/migrations/20260902234624_public_invoice_gst_qst_flag.sql` (reference only)
- new forward migration

### Tasks

- Recreate these functions with `security definer set search_path = ''` and fully qualify every table/function/operator that needs qualification:
  - `public.get_public_invoice(uuid)`;
  - `public.mark_public_invoice_viewed(uuid)`;
  - `public.get_invoice_checkout_state(uuid)`.
- Explicitly revoke function execution from `public`, `anon`, and `authenticated` after each recreation, then grant only:
  - `get_public_invoice`: `anon`, `authenticated`;
  - `mark_public_invoice_viewed`: `anon`, `authenticated`;
  - `get_invoice_checkout_state`: `service_role` only.
- Remove `public_token` from the JSON returned by `get_public_invoice`; the caller already has it and no current public UI consumer uses the returned copy.
- Change the view marker predicate to include `and viewed_at is null`. This makes repeated views no-ops instead of writes.
- Keep the status restriction to `sent` and `paid`.
- Preserve the intentionally required invoice fields, but review whether client email and full postal address need to appear on the public HTML page. Prefer the minimum necessary billing fields.
- Add default function privilege hardening in a carefully reviewed migration if compatible with the project:

```sql
alter default privileges in schema public
  revoke execute on functions from public, anon, authenticated;
```

Do not run a blanket revoke without explicitly regranting every application RPC and testing it.

Supabase recommends an empty search path plus schema-qualified objects for `security definer` functions and notes that functions are executable by roles by default: [Supabase database functions security guidance](https://supabase.com/docs/guides/database/functions#security-definer-vs-invoker).

### Tests

- Assert exact `has_function_privilege` results for `anon`, `authenticated`, and `service_role`.
- Assert that a direct `anon` call to checkout-state fails with `42501`.
- Assert the public payload does not contain `user_id`, internal invoice/client/item/payment IDs, private notes, Stripe IDs/URLs, payment references, push information, or `public_token`.
- Call `mark_public_invoice_viewed` twice and assert the second call does not change `viewed_at` or `updated_at`.

## Phase 5 — Make Stripe payment handling race-safe and abuse-resistant

### Files

- `src/app/api/stripe/checkout/route.ts`
- `src/app/api/stripe/webhook/route.ts`
- `src/lib/public-invoice.ts`
- `src/lib/payments/sync.ts`
- new migration(s) and tests

### Checkout tasks

- Validate `Content-Type` and reject oversized request bodies before parsing.
- Continue deriving invoice ID, currency, and amount from the server/database, never the form.
- Rate-limit by a privacy-preserving combination of IP and token hash. Do not store raw invoice tokens in the limiter. Return `429` with `Retry-After`.
- Prevent multiple active Checkout Sessions for the same invoice/balance. Store the active session ID, expected amount, and creation/expiry state server-side and reuse or safely replace it.
- Use a Stripe idempotency key derived from a stable internal invoice ID plus a version/balance revision, not the public token.
- Remove `public_token` from Stripe metadata. Keep only the minimum stable internal reconciliation fields. Note that success/cancel URLs still necessarily contain the link unless the return flow is redesigned.
- Narrow the proxy public-route match from all `/api/stripe/*` routes to exactly checkout and webhook.

### Webhook tasks

- Preserve raw-body signature verification. Never parse JSON before verification.
- Validate all signed object invariants before inserting:
  - event type is expected;
  - session mode is `payment`;
  - payment status is `paid`;
  - `client_reference_id` equals the metadata invoice ID;
  - invoice ID/user ID are valid UUIDs;
  - `session.currency` exactly matches the stored invoice currency case-insensitively;
  - `amount_total` is a positive safe integer;
  - the session ID matches a session created/stored for that invoice;
  - invoice is not void.
- Record Stripe `event.id` in a dedicated webhook-events table with a unique constraint. Keep the existing unique constraint on Checkout Session ID as a second layer. Stripe recommends tracking event IDs because duplicate delivery can occur.
- Move “lock invoice, read balance, insert payment, update invoice status, mark event processed” into one database transaction/RPC. Lock the invoice row (`FOR UPDATE`) or use an equivalent transactional serialization strategy.
- Decide and test overpayment behavior. Recommended: prevent creating duplicate sessions, record the actual settled amount, mark/alert an explicit overpayment state, and never silently discard money Stripe actually collected.
- Return a 2xx quickly after durable recording. Move PDF/email/push side effects to a retryable outbox/job. A notification failure must not roll back or duplicate a payment.
- Log only Stripe event/session IDs and internal record IDs. Never log full payloads, client addresses, emails, or public tokens.

Stripe requires raw-body signature verification and recommends duplicate-event handling and fast 2xx responses: [Stripe webhook security and best practices](https://docs.stripe.com/webhooks).

### Concurrency tests

- Two identical deliveries of one event create exactly one payment.
- Two different events for the same session create exactly one payment.
- Two concurrently completed sessions cannot silently overpay or corrupt status.
- Manual payment and webhook arriving concurrently produce deterministic balance/status.
- Wrong currency, wrong client reference, unknown session, invalid metadata, unsigned body, and void invoice are rejected without data changes.
- A notification job can retry without creating another payment or receipt record.

## Live Supabase verification checklist

Run read-only checks first in the production project. Save results privately; they may reveal schema details.

### 1. Confirm RLS on every exposed table

```sql
select schemaname, tablename, rowsecurity
from pg_tables
where schemaname in ('public', 'storage')
order by schemaname, tablename;
```

Every application table in `public` must show `rowsecurity = true`. Review any table present in production but absent from Git.

### 2. Inventory policies

```sql
select schemaname, tablename, policyname, roles, cmd, qual, with_check
from pg_policies
where schemaname in ('public', 'storage')
order by schemaname, tablename, policyname;
```

Confirm policy expressions match the final migration. Pay special attention to invoice/client ownership and any storage buckets.

### 3. Inventory table grants

```sql
select table_schema, table_name, grantee, privilege_type
from information_schema.role_table_grants
where table_schema = 'public'
  and grantee in ('anon', 'authenticated', 'service_role')
order by table_name, grantee, privilege_type;
```

Expected: `anon` has no direct table privileges. `authenticated` has only the operations required by the app. `service_role` is inherently privileged and must never reach the browser.

### 4. Inventory callable functions

```sql
select
  n.nspname as schema_name,
  p.proname,
  p.prosecdef as security_definer,
  p.proconfig,
  has_function_privilege('anon', p.oid, 'execute') as anon_execute,
  has_function_privilege('authenticated', p.oid, 'execute') as authenticated_execute,
  has_function_privilege('service_role', p.oid, 'execute') as service_execute
from pg_proc p
join pg_namespace n on n.oid = p.pronamespace
where n.nspname in ('public', 'private')
order by n.nspname, p.proname;
```

Verify every `security_definer` function has an intentional owner, empty search path, fully qualified objects, and exact grants.
